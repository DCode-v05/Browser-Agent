# Web threats to a browser agent, beyond prompt injection

Researched on the web on 2026-10-07.

## Summary

Beyond prompt injection, a browser agent faces threats a plain human browser also faces — phishing, malware downloads, deceptive UI, drive-by cryptomining, OAuth consent phishing, redirect chains — plus a few that are sharper for an agent: it trusts coordinates and accessibility snapshots a page can manipulate, it may have a code-execution tool a "ClickFix"-style page could try to trigger, and on `takeover_chrome` it acts with the person's real, signed-in identity, which turns ordinary phishing and consent-grant abuse into full account takeover. Free, no-new-dependency data sources exist and cover real ground: URLhaus/ThreatFox (CC0 data, free fair-use API) for known-malware URLs, RDAP (no key) for domain age, and DNS-resolver options (Quad9, Cloudflare Families) as a zero-code deployment backstop. Google Safe Browsing is free but its terms restrict commercial use without a separate agreement — worth a legal check before relying on it. Every competitor with published detail (Claude in Chrome, OpenAI Atlas, Gemini in Chrome) converges on the same two moves: shrink what the agent can reach (category blocks, origin restriction, a narrower tool surface) and add a human checkpoint keyed to the sensitivity of the *site*, not just the wording of the control being clicked. A third-party report (hCaptcha, a bot-detection vendor, so read with that interest in mind) found that today's commercial browser agents attempt nearly every tested abuse scenario with no jailbreak needed — a reminder that "misuse by the agent's own user" is a live gap industry-wide, not just for us. One concrete, checked-in-code finding: `bap-browser`'s own address policy already strips URL userinfo correctly (`rpartition("@")`), so it is not vulnerable to the exact bypass that hit the open-source Browser Use framework in the wild.

## 1. Threat catalogue (beyond prompt injection)

This list excludes prompt injection itself (see `docs/research/prompt-injection.md`) but includes threats that are *delivered through* a malicious page without needing an injected instruction — the page just has to be bad, or the agent just has to be fooled visually or technically.

| Threat | How it hurts the agent or person | Backend it matters most on | Sources |
|---|---|---|---|
| **Malicious/phishing site reached by navigation, link, or redirect** | Agent (or the person watching) is shown a fake login/payment page; credentials, card data, or approvals get given to an attacker | All three — the core risk this whole document is about | Covered throughout §2–3 below |
| **Drive-by and malicious downloads** | A page auto-triggers or lures a download of malware, a malicious Office macro file, or an executable; the engine's own "download into a folder, cap the size" rule (spec §5.8) does not inspect *content*, only size and arrival timing | `remote_headless` (files land in the container — contained, but still a foothold); `takeover_chrome` and `bundled_chromium` (files land on the person's real machine — much higher impact) | Vendor docs: Chromium Mark-of-the-Web/quarantine behaviour (`textslashplain.com`, `outflank.nl`); Safe Browsing download protection is part of the same vendor family as §2 |
| **Browser permission prompts abused** (camera, microphone, location, notifications, clipboard) | A page requests a sensitive capability; if granted, the page can surveil through camera/mic, track location, or push deceptive notifications later | `takeover_chrome` most (real device, real account); `remote_headless` less (ephemeral container, but still a privacy/clipboard risk if the engine clipboard-shares) | Vendor/framework: `web.dev` permissions-best-practices; academic: Unibe/NDSS papers on permission-prompt inconsistencies across browsers |
| **Clickjacking / invisible overlays directed at the agent itself** | Classic clickjacking defends a human from an invisible iframe; for an agent the risk is inverted and arguably worse: the agent trusts its own accessibility-tree snapshot and ref coordinates (spec §5.4–§6.1), so a page that visually overlaps a benign-looking element with a different, invisible interactive element can make the agent "click the button it meant to" while actually triggering something else. This is UI redressing against automation, not against a human eye | All three, but highest-stakes on `takeover_chrome` (real session) | Framework: standard clickjacking literature (`X-Frame-Options`, `frame-ancestors`); the agent-specific framing is this document's own inference — no vendor source discusses it directly for AI agents |
| **Deceptive UI: fake buttons, fake system dialogs, fake CAPTCHAs, "ClickFix"** | A page shows a fake "Verify you are human" or fake OS dialog that instructs the viewer (human or agent) to open a Run dialog or terminal and paste a command, which downloads/executes malware. For an agent with any code-execution tool (spec §7, the code tool) or clipboard access, a ClickFix-style page could try to get the agent itself to copy and "run" a command | All three; most dangerous wherever the agent has a code-execution tool or the clipboard, and the backend has real OS access (`takeover_chrome`, `bundled_chromium`) | Third-party/vendor security research: BleepingComputer, Varonis, Splunk, Dr.Web — consistent reporting through 2024–2025 that ClickFix has become one of the most common initial-access techniques |
| **Credential and personal-data leakage: typing into the wrong site** | The agent is asked to "log in" and types a password, card number, or one-time code into a look-alike or compromised page because nothing checked that the page is the genuine site | `takeover_chrome` (real credentials) ≫ `bundled_chromium` (app's own stored logins) > `remote_headless` (usually no stored identity) | This document's §3 heuristics; spec §8.4/§8.6 already route sign-in, payment and one-time-code entry to a human on `takeover_chrome` |
| **Autofill-triggered leakage** | Some phishing pages abuse invisible or iframe-based forms so that an autofilling browser/extension silently submits stored credentials without any explicit "type password" action the engine could gate | `takeover_chrome` (the person's own autofill/password manager is live) | Vendor/third-party: 1Password, Bitwarden, Dashlane docs on "manual" vs "automatic" autofill as the mitigation; `palant.info` and Princeton CITP research on sweep/iframe autofill attacks |
| **Data exfiltration through ordinary page primitives** (form POST, URL query string, `<img>` beacon, CSS attribute-selector exfiltration, WebSocket) | Independent of prompt injection, any page the agent is on can send whatever it can see (including read-only page content with sensitive data in view) onward via these primitives the instant the agent causes any network activity — or even the page's own first-party scripts could do it without any agent action at all | All three; depends on the egress policy (spec §8.1) applying to *every* outbound connection the page itself makes, not just agent-initiated navigation | Third-party/vendor: PortSwigger "Blind CSS Exfiltration," Ruhr-Universität Bochum "Scriptless Attacks" paper, OWASP-adjacent writeups |
| **Payment and purchase risk** | The agent is induced (by a convincing but fake store, or a real store with a confusing flow) to complete an unintended or fraudulent purchase | `takeover_chrome` (real payment methods); `bundled_chromium` if cards are stored in-app | Spec §8.6 already treats "pay/buy/order" as consequential actions needing approval every time — this threat is about the page being deceptive about *what* is being bought, which approval alone does not detect |
| **OAuth consent phishing ("grant access")** | A real identity provider's own consent screen is used to trick the (human or agent) into granting a malicious third-party app broad, often long-lived (refresh-token) access to the real account — no fake login page, no malware, MFA does not help | `takeover_chrome` (real identity, real OAuth grants) | Vendor: Microsoft Learn "Defending Against Illicit Consent Grants"; third-party: SlashID, Dark Reading, Sophos (device-code-flow variant) |
| **Cross-site actions riding the person's cookies — session/cookie takeover** | Because `takeover_chrome` acts with the person's real, signed-in session (spec §4.2), any action the agent is tricked or misused into performing executes with full standing privilege — and separately, if any extension-level bug let session cookies leak, an attacker could hijack the session outright without ever phishing a password | `takeover_chrome` specifically — this is "the largest risk in the product" per spec §8.8 | Third-party/academic: arXiv "Towards Browser Controls to Protect Cookies from Malicious Extensions," Socket/Sonar reporting on real extension-based cookie theft incidents (Cyberhaven and others) |
| **Cryptojacking and resource abuse** | A page runs WebAssembly-based crypto-mining or other heavy background computation, consuming CPU/GPU and, in a metered cloud container, running up cost | `remote_headless` (direct infra cost); less relevant to `takeover_chrome`/`bundled_chromium` beyond battery/perf annoyance | Academic: arXiv "Web-based Cryptojacking in the Wild," NDSS "MINOS" detection paper |
| **Popups and redirect chains** | A page opens new windows or chains redirects through ad-tech infrastructure to eventually land on malware/scam/adult content, possibly faster than any per-navigation check can react | All three; spec §8.1 already judges every new window/frame navigation against the same address policy, with a known limit that "the first request of a window a page opens may reach the network before the window is closed" | Third-party: HUMAN Security, CloudSEK reporting on redirect-chain malvertising infrastructure |
| **Misuse of the agent by its own user** (spam, fraud, scraping against ToS, credential stuffing, card testing, impersonation) | The product itself becomes the attack tool — this is a risk to the *operator* (legal/abuse exposure) and to third-party sites, not to the person watching | All three equally — this is a policy/classifier problem, not a backend-specific one | Third-party: hCaptcha Threat Analysis Group report testing 5 commercial browser agents (ChatGPT Atlas, Claude, Gemini, Manus, Comet) against 20 abuse scenarios — found all five attempted nearly every malicious request tested, "no evidence of any principled safety gating" in some cases. **This is a vendor with a commercial interest in bot-detection (hCaptcha), so treat the framing as motivated, but the described test methodology and per-product results are concrete and checkable** |
| **Sandbox / host escape — cloud backend** | A compromised renderer (via a browser 0-day or a malicious page exploiting a real Chromium bug) tries to escape the browser's own process sandbox and then the micro-VM/container around it | `remote_headless` | Vendor: Chromium's own site-isolation and compromised-renderer threat-model docs (`chromium.googlesource.com`); third-party comparison of gVisor vs Firecracker-style microVM isolation for untrusted workloads |
| **Sandbox / host escape — desktop backend (Electron)** | The desktop app's bundled Chromium pane, if misconfigured, could let a malicious page reach Node.js/OS APIs through the Electron host rather than through the sanctioned bridge channel | `bundled_chromium` | Vendor: Electron's own security-checklist docs (`contextIsolation`, disabling `nodeIntegration`, enabling the Chromium sandbox per renderer) |

**Note on scope:** several entries above (exfiltration, OAuth consent phishing, cookie takeover) are *amplified* by prompt injection but do not require it — a legitimately-looking page, a real identity provider's own consent screen, or a buggy extension can produce the same harm with no injected instruction at all. That is why they belong here rather than in the prompt-injection document.

**Reading for our engine:** every DNS-resolver-based option (Cloudflare Families, Quad9) is zero-code — a deployment/config choice, not something `bap-browser` queries. Safe Browsing's Update API and URLhaus/ThreatFox are the most promising per-URL-check sources that need no new Python dependency and have an explicit free commercial-friendly licence (URLhaus/ThreatFox) or an explicit non-commercial restriction to watch (Safe Browsing — confirm whether an internal engineering tool counts as "commercial purposes" before relying on it in a paid product).

## 3. Heuristics without a feed

Each needs no external feed; all can run offline once the engine has the URL and (for some) the allow/popular-domain list already in config.

| Heuristic | How it works | False positives | Cost |
|---|---|---|---|
| **Newly registered domain** | RDAP query (free, no key, server discovered via the IANA bootstrap registry, per RFC 9224) returns the domain's registration date; flag domains younger than a threshold (e.g. 30 days) | Legitimate new businesses, new marketing campaign pages, new short-lived company sub-brands. High positive rate on a young domain *in general*, but most agent tasks don't need young domains, so an extra approval step is cheap | Low: one RDAP call per new host, cacheable for the session; stdlib `urllib`/sockets can do the HTTP/JSON call, no new dependency (third-party/vendor-neutral source, RFC 9224) |
| **Typosquatting via edit distance** | Levenshtein/Damerau-Levenshtein distance from the visited host to each entry in the allow-list or a short list of top sites the user frequents; flag a close-but-not-exact match (e.g. distance 1-2, or one transposed/substituted/inserted character) | Legitimately similar brand names, hyphenated/regional variants of a real company's own domains, short domain names where small distances are common by chance | Very low: pure string computation, no network. Needs a reference list (the engine's own allow-list is a natural one; a public "popular domains" list, e.g. Tranco/majestic, would be an added data file) (third-party inference, not vendor-confirmed) |
| **Homograph / mixed-script / confusable detection** | Convert to punycode (`xn--`) and back; if the Unicode label mixes scripts or its UTS #39 "skeleton" (confusables.txt) matches a known/allowed domain's skeleton while the raw strings differ, flag it. A plain ASCII-only domain needs no check | Some legitimate regional brands register IDNs intentionally; a small number of real company names use mixed scripts or diacritics on purpose | Low-moderate: needs the Unicode confusables data table bundled (a data file, not a package) and `idna`/stdlib `encodings.idna` or similar for punycode round-trips; this is standard-library-capable in Python with `str.encode('idna')` for basic cases, but full UTS #39 skeleton matching needs the confusables table shipped as data (vendor source: unicode.org/reports/tr39) |
| **Suspicious / abused TLD** | Static list of TLDs with high reported phishing/malware share (community sources cite `.zip`, `.top`, `.xyz`, `.shop`, `.bond`, `.review`, etc. — numbers not independently verified here, third-party source) | High: many legitimate sites use `.xyz`/`.shop`; TLD alone is weak evidence and drifts over time as abuse patterns shift | Very low: a static list check, cheap but needs periodic manual review to stay useful |
| **IP-literal host** (navigating straight to an IP address instead of a domain) | Parse the host; if it is a bare IPv4/IPv6 literal (any spelling — decimal, hex, octal, IPv6, per the engine's own address-policy normalisation already in section 8.1), flag it | Legitimate internal tools, some CDNs/test environments, local development the person is doing on purpose | Very low: the engine already normalises every IP spelling for the address policy (section 8.1); this heuristic reuses that normalisation, no new code path needed beyond a flag |
| **Free hosting / URL-shortener domains** | Static list of well-known free hosting platforms and shortener domains/subdomain patterns that are disproportionately abused for phishing redirects (third-party/community source, e.g. Sublime Security's detection rules cite redirectors leading to `.zip` downloads) | High on free hosting (many legitimate personal/small-business sites); shorteners are also used heavily for legitimate marketing/social links | Low: static list, needs upkeep as new free-hosting platforms appear |
| **`data:` and `blob:` URI pages** | Flag or require approval whenever the active page's own address is a `data:` or `blob:` URI showing a login-like form. These never touch the network when rendered (the "page" is assembled from a local blob or inline data, so there is nothing for Safe Browsing/URLhaus to have ever seen), which is exactly the blob-URI phishing technique reported in 2022-2024 (third-party source: Cofense, malwaretips, hackread) | Legitimate uses of `blob:`/`data:` exist (file previews, exported reports, some SPA download flows), so a blanket block would break real pages; a flag + approval on a *form submission* from such a page is more targeted | Very low: the engine already allows `data`/`blob` in `safety.allowed_schemes` by default (confirmed in `src/bap_browser/config.py`) — this heuristic is about watching what happens *after* arrival at such a page, not about the navigation check itself |
| **Certificate problems** | Playwright/CDP surfaces TLS certificate state; flag self-signed, expired, hostname-mismatched, or (for `remote_headless`) any certificate error that the engine is currently told to ignore via `ignore_https_errors` (already flagged in config as "development only") | Legitimate self-signed internal tools during development; captive portals | Low: data is already available from the browser's own TLS handshake, no extra fetch |
| **Login form domain mismatch / brand impersonation** | Compare the page's visible branding (title, prominent logo/favicon, or text claiming to be a known brand) against the actual host; also compare a form's `action` target host against the page's own host. Academic/third-party literature (brand-domain-identification research) checks form-action domain, logo domain, and cookie domain against the claimed brand | Legitimate third-party payment/SSO/form providers (Stripe, Auth0, a payment processor's own domain) routinely host a form whose action domain differs from the brand the user thinks they're on — this is the single biggest source of false positives for this heuristic | Moderate: needs either a simple favicon/title keyword match against a small watch-list of brands the deployment cares about (cheap), or a generic classifier (expensive, out of scope without a dependency) |
| **"Page claims to be X but is really Y"** | A specific case of the above: compare the page's own claimed identity (title, OG tags, visible "Sign in to X" text) against the resolved host/domain the engine is actually on | Same as above — third-party embeds, white-labelled portals | Cheap if done as a keyword/string check; expensive if done with any ML/vision model |

**Design note:** several of these heuristics reuse data the engine already computes for section 8.1 (address normalisation, IP-literal detection, scheme checks) — extending that existing pass rather than adding a parallel one keeps the surface small, consistent with "every tunable value lives in config.py."

## 4. What existing browser-agent products do

| Product | What it does for web threats (beyond prompt injection) | Source |
|---|---|---|
| **Claude in Chrome** (Anthropic) | Confirmed by reading the primary post directly (`claude.com/blog/claude-for-chrome`, the current location — `anthropic.com/news/claude-for-chrome` redirects there): "blocked Claude from using websites from certain high-risk categories such as financial services, adult content, and pirated content." Site-level permissions let the person grant/revoke access per site. Action confirmations required for high-risk activities (publishing, purchasing, sharing personal data). Advanced classifiers for suspicious instruction patterns and unusual data-access requests. Anthropic's own disclosed numbers: general autonomous-mode attack success rate fell from 23.6% to 11.2% with safety mitigations; on a narrower "challenge" set of four browser-specific attack types, it fell from 35.7% to 0% — Anthropic's own disclosure, not independently reproduced here | Vendor (primary, directly read): `claude.com/blog/claude-for-chrome` |
| **OpenAI ChatGPT Atlas / Agent mode** | Cannot run code in the browser, download files, or install extensions, and cannot touch other apps or the file system — a much narrower tool surface than `bap-browser`'s (which has a code tool and file upload/download). "Watch Mode": pauses and requires the tab to stay active/foregrounded on sensitive sites (named example: financial institutions); abandoning the tab pauses the agent. Offers a "logged-out mode" that never carries the person's existing cookies, specifically to cap the blast radius of a successful injection or deception | Vendor: `help.openai.com` Atlas agent-mode articles, `openai.com/index/introducing-chatgpt-atlas` |
| **Gemini in Chrome** (Google) | Layered design announced for agentic browsing (per third-party reporting of a Dec 8 2025 Google announcement, not independently verified on a primary Google blog in this research pass): a separate, isolated "User Alignment Critic" model reviews every action the primary agent proposes before it executes, specifically so a prompt-compromised primary model cannot also compromise the reviewer. "Origin Sets" restrict what sites/iframes the agent can see at all — unrelated origins, including iframes, are withheld from the agent's view entirely, and a trusted gating step is required before the agent's view expands to a new origin. Mandatory human confirmation for sensitive operations (banking sites, releasing a saved password). A dedicated prompt-injection classifier runs alongside Safe Browsing and on-device scam detection. Separately, Enhanced Safe Browsing already uses an on-device Gemini Nano model to catch tech-support scams, fake virus alerts and deceptive sweepstakes pages — this part predates and is independent of the agentic features | Third-party: BleepingComputer report on the Dec 2025 announcement; vendor: Google Security Blog category pages (could not confirm every detail on a primary Google post in this pass — treat the UAC/Origin Set description as third-party-reported, not vendor-primary-confirmed) |
| **Browser Use** (open-source agent framework) | Ships a deny-by-default `allowed_domains` allow-list the agent must respect. A real, fixed vulnerability (version 0.1.44) shows the risk class directly: an attacker could bypass the allow-list check by putting a decoy allowed domain in the URL's userinfo portion (`https://example.com:pass@malicious-site.com`), since a naive parser reads `example.com` as the host; fixed in 0.1.45. **We confirmed by reading `bap-browser`'s own address-policy code (`src/bap_browser/policy/url_policy.py` line 89) that it already takes `netloc.rpartition("@")[2]` — the text after the *last* `@` — before judging the host, which is not vulnerable to this specific trick.** This is our own code reading, not a third-party claim | Third-party: vulnerability write-up referenced via `mcp.depscope.dev/bugs/pypi/browser-use`; verification against our own code is this research's own finding |
| **Browserbase / Steel.dev** (cloud browser infrastructure for agents) | Both sell isolated, ephemeral cloud browser sessions as their core product — i.e., the `remote_headless` backend's problem space is their entire business. Steel (open-source) bundles session management, anti-detection, ad-blocking and proxy support; Browserbase is the managed/enterprise equivalent. Neither vendor page reviewed here goes into their own sandbox/VM isolation technology in the depth this research targeted (e.g. whether they use gVisor/Firecracker-class isolation specifically) — **this is a gap in what this research could confirm, not a confirmed absence** | Vendor comparison pages (`steel.dev/blog/steel-vs-browserbase...`, `keywordsai.co` market map) — thin on isolation internals |
| **Perplexity Comet** | Perplexity states (per third-party reporting) that every "Computer" task runs in an isolated microVM, and that both Comet and "Computer" use a content-screening layer ("BrowseSafe") specifically to screen retrieved content for prompt injection before the model sees it. After the disclosed "CometJacking" prompt-injection issue, Perplexity added visual confirmation before sensitive actions. Separately, independent research reported that Comet sends the URLs the person visits to Perplexity's own servers with no way to disable this — a privacy-relevant data flow unrelated to any attack, worth noting for the architecture comparison | Third-party: `digg.com` sandboxing/guardrails report, `blog.rankiteo.com` CometJacking write-ups, `shivankaul.com/blog/comet-privacy` (independent researcher, not vendor-confirmed) |

**Reading for our engine:** two patterns recur across every product that has published anything concrete: (1) **shrink what the agent can even see or reach** — category blocks (Claude), Origin Sets (Gemini), tight tool surface plus logged-out mode (Atlas) — rather than only trying to classify bad content after the fact; and (2) **force a human checkpoint tied to the sensitivity of the destination**, not just the tool being called — "financial institution" and "release a saved password" are site/data-sensitive triggers, distinct from `bap-browser`'s current `consequential_words` approach (spec §8.6), which is a wording-on-the-control trigger. Our address policy's allow/block lists already give us the Origin-Set-like lever; we do not yet have an explicit "sensitive site category" concept distinct from the domain allow-list.

## 5. Coverage check against OWASP

Sources: OWASP GenAI Security Project, `genai.owasp.org` (vendor/framework source — OWASP is a non-profit standards body, treated here as a framework-grade source, not an independent academic one).

### OWASP Top 10 for LLM Applications 2025 (v2.0, published 18 Nov 2024)

Only items that bear on web threats (not prompt injection, already covered elsewhere):

| ID | Name | Bears on web threats how | Where it lands in our engine |
|---|---|---|---|
| LLM02 | Sensitive Information Disclosure | A malicious or deceptive page can surface content designed to make the model restate secrets it can see (page content, not instructions) | Partly: spec §8.3 already keeps passwords, typed text and redacted patterns from the model/log; nothing currently screens *page content the model reads* for secrets belonging to someone else |
| LLM03 | Supply Chain | Not primarily a web-threat item for us — applies more to model/plugin supply chain. Marginal relevance: a compromised npm/PyPI dependency pulled into the viewer or engine | Out of scope for this document; project rule "ask before adding a dependency" is the existing control |
| LLM05 | Improper Output Handling | If the agent's output (e.g. generated text) is later rendered unsanitised somewhere, that's an XSS-adjacent risk — more relevant to the viewer than the engine | Not assessed here; flag for the viewer's own security review |
| LLM06 | Excessive Agency | The core "how much can this agent do without a human" question — directly our §8.2 approval/policy model and §8.6 consequential actions | Addressed by design; the open question is whether the *scope* of what counts as consequential matches what deceptive sites actually target (payment, consent, data release) |
| LLM09 | Misinformation | A deceptive page could cause the agent to report false information as fact to the person (e.g. a fake "order confirmed" page) | Not currently a distinct check; overlaps with "page claims to be X" heuristic in §3 |
| LLM10 | Unbounded Consumption | Cryptojacking and resource-abuse pages (§1) are a web-delivered instance of this | Not currently addressed; no CPU/resource cap on page execution found in the spec sections read |

LLM01 (Prompt Injection), LLM04 (Data/Model Poisoning), LLM07 (System Prompt Leakage), LLM08 (Vector/Embedding Weaknesses) are out of scope for this document (LLM01 belongs to the prompt-injection document; LLM04/07/08 don't bear materially on web threats to a browser agent).

### OWASP Top 10 for Agentic Applications (ASI01–ASI10, published 9 Dec 2025)

| ID | Name | Bears on web threats how | Where it lands in our engine |
|---|---|---|---|
| ASI01 | Agent Goal Hijack | The prompt-injection document's territory primarily, but a deceptive (non-injecting) page that simply lies about what a button does can hijack the goal too | Partly our §1 "deceptive UI" and "page claims to be X" entries |
| ASI02 | Tool Misuse | A deceptive page tricking the agent into using `browser_upload_file`, the code tool, or payment flows for an unintended purpose | Spec §8.2 approvals and §8.6 consequential-action gating are the existing control; this document's heuristics (§3) are additional *input* to deciding when to gate |
| ASI03 | Identity & Privilege Abuse | Exactly our "cross-site actions riding the person's cookies" and "OAuth consent phishing" entries (§1) — `takeover_chrome` acting with the person's real identity is the whole risk | Spec §8.8 names this as "the largest risk in the product"; OAuth consent phishing specifically is not yet a named check anywhere in the spec sections read |
| ASI04 | Agentic Supply Chain Vulnerabilities | Not primarily a web-threat item; relevant to how `bap-browser` itself is built/distributed, not to sites it visits | Out of scope here |
| ASI05 | Unexpected Code Execution | The code tool (spec §7) and ClickFix-style pages (§1) both land here: a page tricking the agent into treating attacker text as a command to run | Spec §7.4 ("Limits and safety" on the code tool) is the existing control for the tool itself; ClickFix-style deception of the agent is not yet a named defence |
| ASI06 | Memory & Context Poisoning | Prompt-injection document's territory (persistent/stored instructions) | Out of scope for this document |
| ASI07 | Insecure Inter-Agent Communication | `bap-browser` is single-agent-driven per session as far as the spec sections read show; no inter-agent protocol in scope | Not applicable currently |
| ASI08 | Cascading Failures | A false "download succeeded"/"payment confirmed" signal from a deceptive page feeding into a longer automated pipeline the agent runs unattended | Not addressed; relevant if/when the engine supports longer unattended task chains |
| ASI09 | Human-Agent Trust Exploitation | A confident but wrong agent explanation ("this is the official site") leading the person to approve something they shouldn't — the flip side of every approval-card interaction in spec §8.2 | The approval card shows the raw action, not the agent's claim about the site, which limits (but does not eliminate) this risk |
| ASI10 | Rogue Agents | Out of scope — `bap-browser` does not claim autonomous self-direction beyond the task it's given | Not applicable |

**Overall reading:** our strongest existing coverage is ASI02/ASI03 (tool policy, approvals, the "largest risk" framing for take-over Chrome) and LLM06 (excessive agency, via the same approval system). The clearest gaps against this checklist are OAuth consent phishing (ASI03's sharpest web-specific form), resource-abuse/cryptojacking (LLM10), and any check that compares what a page *claims* to be against what it *is* (ASI01/ASI09, LLM09) — none of which the spec sections read name explicitly today.

## 6. Recommended safeguards for our engine

Ordered highest value-for-cost first. "Cost" means engineering + dependency + ongoing-upkeep cost, not runtime latency alone. None of these require a new third-party Python package unless stated.

1. **Extend the existing address-normalisation pass (spec §8.1) with free, local flags: IP-literal host, `data:`/`blob:` page submitting a form, bare-IP-in-address-bar, and the TLS certificate state Playwright/CDP already exposes.** All of this data is already computed or trivially available in the same place the engine already judges every navigation. Cost: very low (no new network call, no new dependency). Value: closes a real, documented gap — the config today allows `data`/`blob` schemes by default, which is exactly the delivery mechanism reported for blob-URI credential phishing. Backend: all three. Sources: §3 heuristics table above; `config.py` read directly.

2. **Add URLhaus and ThreatFox as an optional per-navigation or per-download check, gated by its own config flag.** Both are free, CC0-licensed (explicitly allows commercial use), need only an HTTPS POST with a free Auth-Key — no new Python dependency, stdlib `urllib`/`http.client` suffices. Cache per-host like `policy_cache_s` already does for the address policy. This is the best-covered, least-legally-ambiguous per-URL malware feed available to us. Cost: low (one new config section, one HTTP call pattern already used elsewhere in the codebase's style). Value: moderate-high — catches known malware-hosting URLs and C2 infrastructure, which Safe Browsing's free tier would also catch but with a cleaner commercial licence. Backend: all three, most valuable on `takeover_chrome`/`bundled_chromium` where a successful malware download has real-machine impact. Sources: §2 table (URLhaus, ThreatFox rows).

3. **Add an RDAP-based "newly registered domain" flag for hosts not already on the allow-list.** Free, no API key, standard-library-capable (RFC 9224 bootstrap discovery, plain JSON over HTTPS). Use it to add a step to the approval flow (not an outright block — false-positive rate is too high for that) when the agent is about to act on a domain registered in, say, the last 30 days. Cost: low. Value: moderate — catches freshly-stood-up phishing infrastructure that no blocklist has caught up with yet, which is exactly the gap every static feed has by construction. Backend: all three. Sources: §3 heuristics table (RDAP row).

4. **Add typosquatting (edit-distance) and homograph (UTS #39 skeleton) checks specifically against the deployment's own `allowed_domains` list — not against the whole web.** This is cheap because the comparison set is small (the deployment's own allow-list, not a universe of "popular sites"), and it directly protects the exact sites a deployment has said matter (e.g. the person's bank, if allow-listed). Needs the Unicode confusables table bundled as a data file (not a package dependency) for the homograph half; the typosquatting half is pure string distance, no data file needed. Cost: low-moderate (one bundled data file, ask-before-adding-a-dependency rule satisfied since it's data, not code, but worth raising explicitly before pulling in the confusables table). Value: moderate-high, precisely targeted. Backend: all three. Sources: §3 heuristics table; UTS #39 (`unicode.org/reports/tr39`).

5. **Treat a real identity provider's OAuth/consent-grant screen as a new, named human-checkpoint trigger, alongside the existing CAPTCHA/sign-in/2FA human handoff (spec §8.4).** OAuth consent phishing is distinctive: no fake page, no malware, MFA does not help, and it is the sharpest concrete form of ASI03 (Identity & Privilege Abuse) for a product whose entire `takeover_chrome` backend exists to act with a real identity. Detecting "this is a consent/permissions-grant screen, not an ordinary login" needs a small pattern set (URL patterns for major IdPs' consent endpoints, or page-text patterns like "wants to access your"), which is a modest heuristic, not a feed. Cost: moderate (new detector, but reuses the existing `browser_request_human` plumbing). Value: high for `takeover_chrome` specifically, where the "largest risk in the product" (spec §8.8) is precisely identity abuse. Backend: `takeover_chrome` (OAuth grants on a cloud-only session carry little standing value; `bundled_chromium` is a secondary case). Sources: §1 catalogue (OAuth consent phishing row); Microsoft Learn, SlashID.

6. **Extend download handling (spec §5.8) to hash the file after arrival and check the hash against URLhaus/ThreatFox (and optionally Safe Browsing) before telling the agent the download succeeded — not before saving it (the size-after-arrival pattern already established is the right model to extend).** Cost: low-moderate (hashing is free; the lookup reuses recommendation 2's integration). Value: moderate — turns a size-only check into a known-malware check for the one tool category (`browser_upload_file`'s sibling, downloads) that already needs approval by default. Backend: highest value on `takeover_chrome`/`bundled_chromium` (real machine). Sources: §1 catalogue (drive-by/malicious downloads row); §2 table.

7. **Point any cloud-container DNS resolver at Quad9 (9.9.9.9) or Cloudflare's 1.1.1.2, as a deployment-level floor underneath the engine's own checks, specifically for `remote_headless`.** This is pure infrastructure configuration — no code. It will not catch anything the engine's own checks already catch, but it is a free, zero-maintenance backstop against whatever both those checks miss, aggregating 20+ external threat-intel sources neither of which is otherwise available to us for free. Cost: near-zero (ops config). Value: moderate as defense-in-depth, not a primary control. Backend: `remote_headless` (we control that container's resolver; we do not control the person's own machine's resolver on the other two backends). Sources: §2 table (Cloudflare, Quad9 rows).

8. **Define an explicit "sensitive site category" concept (financial, identity/OAuth, healthcare, government) distinct from the plain domain allow/block lists, modelled on what Claude in Chrome and Gemini in Chrome both do.** This is a product-design recommendation, not a data integration: every competitor with published detail either blocks these categories outright or adds a mandatory human checkpoint keyed to the *category* of site, not to the wording on the control being clicked (which is `bap-browser`'s current `consequential_words` approach, spec §8.6). Cost: moderate (needs a maintained category list — either a static list or, longer-term, a reputation-feed lookup like Web Risk's categorisation, which is paid). Value: high — this is the single clearest pattern across every competitor that has published anything concrete. Backend: `takeover_chrome` most, `bundled_chromium` next. Sources: §4 table (Claude in Chrome, Gemini rows).

9. **Flag cryptojacking-style resource abuse on `remote_headless` with a simple CPU/wall-time budget per page, surfaced as a diagnostic rather than a block.** Lower priority than the above because the primary harm is cost, not safety, and `bap-browser` already has `max_size_mb`-style budget patterns to extend from. Cost: moderate (needs a CDP/process-level CPU sampling hook not currently read in the spec sections reviewed). Value: moderate, mostly cost-containment. Backend: `remote_headless`. Sources: §1 catalogue (cryptojacking row).

10. **Add action-pattern detectors for self-abuse (the agent's own user directing it toward card testing, credential stuffing, mass account creation, or scraping against a site's terms), reusing the event/action log the engine already keeps rather than adding new instrumentation.** This is squarely a policy/classifier problem, informed directly by the hCaptcha report's finding that today's commercial browser agents attempt nearly every tested abuse scenario. Cost: moderate (classifier design, not a new network dependency). Value: real but harder to quantify — this protects the operator's own standing (ToS/abuse exposure) more than it protects the person watching. Backend: all three equally. Sources: §1 catalogue (misuse-by-own-user row); hCaptcha Threat Analysis Group report (vendor with a commercial interest in bot detection — treat the framing, not the described findings, with that in mind).

**Not recommended for now:** Google Web Risk (paid, no clear benefit over free URLhaus/ThreatFox for a first pass, and its exact pricing could not be confirmed in this research — see §2); PhishTank (registration reportedly closed since 2020, weaker and more rate-limited than OpenPhish/URLhaus); Microsoft SmartScreen (no public API found at all); MISP/OTX aggregation (would need a new client-library dependency for a benefit already covered by URLhaus/ThreatFox).

## 7. Open questions

- **Does querying Google Safe Browsing from `bap-browser` count as "commercial purposes" under its Terms of Service?** The ToS text found says "you may not use the Safe Browsing API for commercial purposes" without a separate agreement — this needs a legal read against our actual product/pricing model before we rely on it, free alternative (URLhaus/ThreatFox) notwithstanding.
- **What are Web Risk's actual current prices?** Both attempts to fetch `cloud.google.com/web-risk/pricing` and the Web Risk product page returned truncated content; only search-snippet numbers were found ($0.50/1000 for `uris.search` after a 100k free tier, ~$50/1000 for `hashes.search`) and these are **not independently confirmed** — verify directly before budgeting if Web Risk is ever reconsidered.
- **Does Safe Browsing v5's Terms of Service differ from v4's?** The v5 overview and terms pages returned 404s in this research; v5's privacy improvements over v4 are vendor-stated (via the v5 API reference pages, which did load) but its own ToS page could not be located/confirmed separately.
- **Is ThreatFox's search endpoint really key-free?** One community source said the Auth-Key is only required to *submit* indicators, not to search; this is worth a direct, small test call before depending on it, since it contradicts the "same key as URLhaus" framing in other sources.
- **How exactly do Browserbase and Steel.dev isolate sessions at the OS/VM level?** Neither vendor page reviewed in this pass stated whether they use gVisor, Firecracker-class microVMs, or something else — relevant only if we ever consider using one of them as our `remote_headless` infrastructure rather than running our own.
- **What, if anything, should "sensitive site category" (recommendation 8) be built from?** A static, manually maintained list is cheap but will drift; Web Risk's categorisation is paid; no free, maintained "site category" feed was found in this research. This may be a case where a short, manually curated list (financial + major IdPs) is the pragmatic answer rather than any feed.
- **Does Playwright/CDP expose enough TLS certificate detail (self-signed, hostname mismatch, expiry) for heuristic 3's certificate-problem check without extra plumbing?** Not verified against the actual driver code in this research pass — `src/bap_browser/driver/playwright_driver.py` would need a direct read to confirm before estimating recommendation 1's cost precisely.
- **Is the Gemini-in-Chrome "User Alignment Critic" / "Origin Sets" description accurate?** It came from one third-party (BleepingComputer) report of a Google announcement; a primary Google source was not located and read directly in this pass.
