Our System, Hermes and the OpenAI Agents SDK, compared on computer use

Date: 2026-10-10Our System 0b4ae4fHermes dce1e9bOpenAI Agents SDK 125efa0Read from the code, nothing installed or run

Computer use is a system taking over a computer and working on it directly: a screenshot of the screen, the mouse, the keyboard, opening programs, all through the operating system rather than a web page. This page compares the three systems' computer-use modules only. It does not cover the desktop app shell (the chat window), which an earlier page compares: docs/research/desktop-app-comparison.md.

How to read the tables

Sections 4 to 11 hold one table each, in the same shape as the earlier comparison: Row, Our System, Hermes, OpenAI Agents SDK, Best, Why, Gap or idea for Our System. The verdict words are a system's name, Tie (two systems do it equally well), Split (each named system wins a different half of the row), None (none of the three has it), or Not judged (the row describes rather than ranks). Hermes' two modules are written as CU (tools/computer_use/, the real machine) and BD (tools/bot_desktop/, the agent's own contained desktop) wherever they differ.

2. The verdict

Hermes' computer-use module is the most built of the three. It wins 11 of the 20 ranked rows, mostly because its real-machine driver already works on macOS, Windows and Linux, with three ways to let a model see the screen (a plain screenshot, an accessibility tree with numbered overlays, or the tree alone for a model with no vision), image caps, and a screenshot deduplication layer that skips resending an unchanged picture. Its real-machine driving is not Hermes' own code: it speaks MCP to a separate open-source project, cua-driver, and that project's own docs say its macOS path uses "private SkyLight SPIs" that "Apple can change in any OS update." Hermes' own docs name that risk themselves.

Our System wins 3 rows outright, draws 3, and splits 3, and each is a real strength, not a consolation. It is the only one of the three with a model-facing open an app action and an app allowlist that is on by default and enforced twice (the tool itself, and the container's own binary path), where Hermes' allowlist is opt-in only and its own launch_app method is not wired into its tool at all. It is the only one with a benchmark for computer use: 13 tasks modeled on two published research benchmarks, OSWorld and OS-Harm, each graded by a reference solution. It is the only one with end-to-end tests that drive a real screen: a real Docker container, a real Mac helper over real HTTP, a real micro VM image. Hermes has eight times as many computer-use tests, all against mocked or stubbed drivers.

The OpenAI Agents SDK wins no row. It is the cleanest interface of the three to implement against, and its one example (a Playwright-driven browser window) is well built, but it ships no driver for a real operating system at all: no screenshot capping, no app concept, no stop action, no OS permission handling. Every one of those is "none, you build it."

One technical difference runs under several rows and is worth stating plainly: Our System's Mac driver posts real hardware-level input events (CGEventPost to the HID tap), which moves the actual pointer and only reaches the app that is genuinely in front, the same as a person's own hand. Hermes' cua-driver posts events to a specific app's process without moving the pointer or needing that app to be in front, so a person can keep working in the foreground while the agent acts elsewhere. That is a real advantage for Hermes, bought by depending on undocumented internals of the operating system.

What Our System should do next

  1. Wire a screen-change cap into typed text and screenshots the model asks for, the way Hermes skips resending an unchanged picture (B3). Fewer tokens on a long desktop task.
  2. Hold computer_screenshot and computer_zoom back while a person has control, not only the mouse and keyboard (E6). Today a person's own screen is seen even though their keystrokes are not recorded.
  3. Keep the helper off a non-loopback address until the tailnet design (spec 21.16) lands (E5). The --host flag already accepts one today, ahead of the authentication design built for it.
  4. Add an accessibility-tree perception mode, at least for the contained and VM desktops where xdotool's own target already knows window geometry (B1). This is the single biggest perception gap against Hermes.
  5. Build the Windows and Linux (X11) real-machine helpers already specified in spec sections 21.14 and 21.15 (A3). Hermes already runs on both.
  6. Keep the real end-to-end tests and the OSWorld/OS-Harm-modeled task set as the model to defend, not drop for speed (G1, G2). Neither Hermes nor the OpenAI SDK has either.

5. What the model perceives

Row Our System Hermes OpenAI Agents SDK Best Why Gap or idea for Our System
B1 The picture A raw screenshot only, full screen or a 2x crop from computer_zoom. No accessibility tree. The spec lists that as not built. Three modes: som (a screenshot with numbered overlays on every clickable element, plus the OS's own accessibility tree, the default), vision (a plain screenshot), and ax (the tree alone, for a model with no vision). A raw screenshot only. The SDK builds no tree or overlay itself. Hermes A model that cannot see well, or cannot see at all, still has a tree to read. A model with vision gets numbered targets instead of guessing pixel coordinates. An accessibility-tree mode, even a first cut limited to the contained desktop, would close the largest perception gap against Hermes.
B2 Capping and resizing The screenshot is the desktop's configured size (1024x768, 1280x800 or 1366x768) as taken, no further resize. The separate live view the person watches is capped by quality level. The longest edge is capped (1,456px default), a picture under 8x8px is left out entirely, and the accessibility tree sent in text is capped at 100 elements and 120 characters each, with the rest spilled to a capped cache file. None, you build it: the SDK wraps whatever screenshot() returns, unresized. Hermes More layers, and each is a stated, measured number. Cap the model-facing screenshot's longest edge the way the live view already is, so a large screen does not cost more tokens than it needs to.
B3 Sent only when asked Yes by default (computer.picture_after_action is off). An admin can turn on a picture after every action. Yes, and a dedup layer skips resending a picture that has not changed since the last one of the same window, up to twice in a row. No: a screenshot is attached after every batch of actions, whether the model asked for one or not. Hermes The dedup step is a genuine token saving a static screen does not need to pay for again. Skip resending a screenshot whose pixels have not changed since the last one, the way Hermes does.

Not confirmed for a real macOS or Windows machine with no Bot Desktop attached. None, you build it. Split: Our System for its real Mac, Hermes for its contained desktop Each has a genuine, working stop mechanism for one of its two arrangements, and neither has one confirmed for the other. E4 An OS permission the person must grant macOS Screen Recording and Accessibility, requested automatically when the helper starts, with the exact missing permission named until both are granted, then it re-pairs by itself. E5 The channel to a real-machine helper A bearer token, new each start, checked in constant time, over HTTP. E6 What a person does manually Not recorded: the person's own input is tagged apart and excluded from every check. No call writes it to the event log in the files read. BD: stronger than not recording it. While a person holds the lease, the agent's tool cannot even take a screenshot, because, in the system's own words, "the person may be typing a credential." One narrow exception, a thumbnail for the app's own preview, stays local and is not sent to the model. Not applicable. Hermes Refusing to look is a stronger guarantee than looking and choosing not to write down what was typed. 11. Known gaps

Row Our System Hermes OpenAI Agents SDK Best Why Gap or idea for Our System
H1 What each names as not built or limited Its own spec section (21.10), as committed on main, names its gaps plainly: a helper for Windows or Linux, reading apps through their accessibility tree, and a desktop of macOS or Windows itself (only Linux desktops exist, contained or on a VM). Its own docs name several, each a specific, named failure: background input is measurably slower than a direct click, a password must go through the OS's own autofill and never be typed by the agent, some apps (modern Windows UWP apps, older Electron apps on Linux, a few macOS apps with custom drawing) expose no accessibility tree and fall back to clicking by pixel, an administrator-level window on Windows silently reports success while doing nothing ("an OS constraint, not a driver bug"), and the macOS driver's private APIs can change in any OS update. Its own docs name two narrow gaps: an older wire format needs one extra setting a newer one does not, and the safety-check hook is the only review point, with no pause-and-resume for a flagged computer action the way an ordinary tool call gets one. Not judged Each names its own real limits in its own words rather than hiding them. None is more honest than another, only more or less specific. Hermes' list is the most detailed because its built surface is the largest. None beyond what the earlier rows already recommend.

12. Method and limits

What was read. Both other repositories were already cloned outside this repository for an earlier comparison: Hermes at dce1e9b375 (2026-10-09) and the OpenAI Agents SDK at 125efa02 (2026-10-08). Our System was read at main's 0b4ae4f (2026-10-10). Three research agents, one per system, each read their system's computer-use code against one shared checklist of rows, with every claim carrying a path:line they opened, or the spec's own wording for something specified but not built. Nothing was installed, started or called over the network.

A note on Our System's own uncommitted work. This checkout holds uncommitted edits to docs/bap-browser-spec.md (new sections 21.14 to 21.16, for real Windows and Linux helpers) that are not part of this comparison's commit and were not written by this work. A separate branch, worktree-computer-use-helpers, holds the matching code, also not part of main. Neither was read or cited here: every claim about Our System's Windows and Linux support reads the spec exactly as committed on main (git show HEAD:docs/bap-browser-spec.md), where it stops at section 21.13 and names Windows and Linux as not built. Nothing in this checkout's uncommitted state was touched, staged or committed while writing this page.

What I checked by hand. These facts decide verdicts, so I opened each one myself:

  • Our 12 computer_* tool names, read directly from src/bap_browser/tools/computer_tools.py, matching the spec's own list exactly.
  • Our settings keys (runs, helper_url, helper_stop_corner, screen, zoom, picture_after_action, ask_before_apps, mac_any_app), read directly from src/bap_browser/config_computer.py.
  • Our Mac driver posts input with CGEventPost to the HID event tap (src/bap_browser/driver/mac_hands.py:226-230), which moves the real pointer, unlike Hermes' background, no-cursor-move approach.
  • Hermes' doctor.py lists _SUPPORTED_PLATFORMS = ("darwin", "linux", "windows") and has real Linux-specific detection code and tests (tests/computer_use/test_cua_no_overlay.py), confirming its cross-platform support is more than a documentation claim, even though the actual input-driving code lives in the separate cua-driver project, not in Hermes' own repository.
  • cua-driver's own source is not in the Hermes repository: the claim that it posts input without moving the real pointer rests on Hermes' own documentation of it (its docstrings, and a "cursor overlay" setting in cua_backend_driver.py that only makes sense if the pointer stays put), not on reading cua-driver's own code.

Limits.

  • The verdicts judge the code at the commits above. All three repositories change often.
  • Code was read, not run. A feature that exists in code may still fail in use.
  • Not confirmed from code: whether Our System's generic approval floor (pay, send, delete, share) applies to computer-use actions by the same rule it applies to browser actions (E1), whether a stop mechanism exists for Our System's contained and VM desktops, or for a Hermes CU session on a real machine with no Bot Desktop attached (E3), and whether Hermes' live smoke test for computer use runs in CI (G1).
  • The research notes behind this page were kept outside the repository and are not part of it.
